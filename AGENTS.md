# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, etc.) when working with code in this repository. `CLAUDE.md` is a symlink to this file.

`AGENTS_LOCAL.md` exists in the repository root, read it as well: it holds local, machine-specific instructions and is not committed (git-ignored).

DOOM 3 BFG Edition (id Tech 4, GPL) ported to a CMake build on modern Windows. Only 64-bit MSVC (x64) builds are supported; the x86 build was dropped. You need VS2022 or its Build Tools, the Windows 10 SDK, and XAudio2 2.9 (Windows 10+). The legacy DirectX SDK is not used.

## Build

```
cmake --preset vs2022-x64            # configure (VS 2022 generator, x64)
cmake --build --preset release       # also: debug, retail
```

- zlib is a git submodule in `third_party/zlib` (upstream madler/zlib at a release tag), compiled into the `external` target from its `.c` files. After cloning run `git submodule update --init`, or configure stops with that hint.
- The output is `build\vs2022-x64\bin\<Config>\Doom3BFG.exe`. The generated `.sln` in `build\vs2022-x64` can also be opened in Visual Studio.
- For Ninja, run these from an "x64 Native Tools Command Prompt for VS 2022": `cmake --preset ninja-x64`, then `cmake --build --preset ninja-release` (or `ninja-debug`, `ninja-retail`).
- `Retail` is `Release` plus `ID_RETAIL`.
- The language is **C++23**. The root `CMakeLists.txt` sets `CMAKE_CXX_STANDARD 23` and pins `/std:c++23preview` (CMake would otherwise pick `/std:c++latest`), plus `/Zc:__cplusplus`. You need MSVC 19.43 (VS 2022 17.13) or newer.
- C++20 and later imply the `/permissive-` conformance mode. That means:
  - string literals are `const char[]`;
  - two-phase name lookup is enforced;
  - `requires` is a keyword;
  - `==` has reversed candidates, so comparison operators need `const` parameters.
- `doomclassic` and `timidity` keep `/Zc:strictStrings-`, because the 1993 C code passes literals as `char *` everywhere.
- The Direct3D 12 backend needs DXC, the Agility SDK and WARP: `tools\d3d12\install-d3d12-sdk.ps1` downloads them at pinned versions (SHA-256 and Microsoft signatures checked) into `external\d3d12-x64` (gitignored; `-DD3BFG_D3D12_SDK_ROOT=<dir>` points elsewhere), and the configure stops without them. The build copies `dxcompiler.dll` and `dxil.dll` next to the exe and `D3D12Core.dll` and `d3d12SDKLayers.dll` into `D3D12\` beside it: copy both into the game install with the exe (`run-vdemos.ps1` does). `d3d10warp.dll` (WARP with feature level 12_2) goes only next to `d3d12Tests.exe`: its license allows testing, not shipping it.
- Build all three configs after language-level changes. `Debug` and `Retail` compile code that `Release` doesn't (`assert` bodies, `#ifndef ID_RETAIL`).
- Engine code builds at /W4. `-DD3BFG_WARNINGS_AS_ERRORS=ON` adds /WX.
- The Bink videos play through FFmpeg (optional). `tools\ffmpeg\build-ffmpeg-x64.cmd` builds a minimal 64-bit LGPL FFmpeg 7.1 into `external\ffmpeg-x64` (gitignored; needs MSYS2 in `C:\msys64` with `pacman -S make diffutils`), then re-run the configure. CMake finds it there (`-DD3BFG_FFMPEG_ROOT=<dir>` to point elsewhere), defines `USE_FFMPEG` and copies `avformat-61.dll`, `avcodec-61.dll` and `avutil-59.dll` next to the exe. Copy them into the game install with the exe. Without FFmpeg, or without the DLLs at runtime (they are delay-loaded), the videos stay black.

## Tests

`idlibTests` is a console exe (`neo/tests/`) that links the idLib objects plus engine stubs (`idlib_test_stubs.cpp`: NULL `common`/`cvarSystem`/`fileSystem` and `Sys_Milliseconds` etc.). It covers math, MatX, LCP solvers, trace-model mass properties, SIMD-vs-generic joint routines and the global `operator new`/`delete`.

```
cmake --build --preset release --target idlibTests
ctest --test-dir build/vs2022-x64 -C Release
build/vs2022-x64/bin/Release/idlibTests.exe LCP_Symmetric   # one test (substring filter), or "all"
build/vs2022-x64/bin/Release/idlibTests.exe all noftz       # run without FTZ/DAZ
```

- Run the tests in `Release`. Some tests feed out-of-range inputs on purpose. In `Debug`, those trip `assert`, and `AssertFailed` calls `common->Warning` on the NULL stub `common`, so the test crashes.
- The runner enables FTZ/DAZ by default, like the engine, and `noftz` turns that off.
- Set `IDLIB_TESTS_VERBOSE=1` to print every failed check. By default each test prints its first 20.
- `lcp_generic.cpp` recompiles `Lcp.cpp` under renamed classes (`idLCP_*_Generic`) with the SSE macros undefined, so the solvers can be compared. Right now both copies are the same code (see SIMD below).
- `ctest` also runs `renderApiLeaks` (`tools/check-render-api-leaks.ps1`): it fails when any file uses an OpenGL name (the OpenGL backend is removed), or a file outside `neo/renderer/D3D12/` and `neo/tests/d3d12_*` a Direct3D 12, DXGI or DXC name. `precompiled.h` includes no API header, so their types don't compile there either. GL's conventions keep their names (`GLS_*`, `GLMatrix`, `GLClipToD3D`).
- `ctest` also runs `d3d12Tests` (see Direct3D 12 below).
- `ctest` also runs `editorModules` (`tools/check-editor-modules.ps1`): it fails when a file of `editor/ui/` includes an engine or bridge header, one of `editor/bridge/` a Qt header, or one of `editor/api/` and `editor/mtr/` either. `renderApiLeaks` scans `editor/` as well.
- There is no lint step and no other test suite. Game code is checked by running the game and the visual demos (below).

## Architecture

**Single executable.** `neo/CMakeLists.txt` builds `idLib`, `external` (zlib, jpeg, etc.), `Game-d3xp` and `engine` (everything else but `WinMain`) as CMake **OBJECT** libraries and links them straight into `Doom3BFG.exe` with `d3bfg_link_engine`; the exe's own source is `sys/win32/win_entry.cpp`, a `WinMain` that calls `Sys_GameMain`. Static libraries would let the linker drop translation units that hold only self-registering globals (`idCVar`, `idTypeInfo`/`CLASS_DECLARATION`, `idEventDef`, `idCommandLink`), which would silently remove cvars, entity classes and commands. `doomclassic` and `timidity` (classic DOOM 1/2) are ordinary static libs. `amplitude` is a separate tool exe.

**Source lists are explicit.** New `.cpp`/`.h` files must be added to `neo/sources.cmake` (`IDLIB_SOURCES`, `EXTERNAL_SOURCES`, `GAME_D3XP_SOURCES`, `ENGINE_SOURCES`, `DOOMEXE_SOURCES`, `AMPLITUDE_SOURCES`) or `doomclassic/sources.cmake`. Engine files use the precompiled header `neo/idlib/precompiled.h`.

**Layout of `neo/`:**
- `idlib/`: the base library (math, containers, strings, the `idSIMD` processor, the parallel job system).
- `framework/`: common, cvars, the console, the file system, and the main frame loop (`common_frame.cpp`).
- `renderer/`: the frontend, the backend interface `RenderBackend.h` (its contract is the comment at its top) and its one backend, `D3D12/` (below). The OpenGL backend is removed; `git show d647250:neo/renderer/OpenGL/<file>` has its last state.
- `d3xp/`: game logic (entities, AI, physics, scripts), compiled into the same exe rather than as a game DLL.
- `cm/`: the collision model.
- `aas/`: bot/AI navigation.
- `sound/`: XAudio2.
- `swf/`: the Flash-based UI.
- `ui/`: legacy GUIs.
- `sys/win32/`: the platform layer (the window in `win_window.cpp`, the WGL context in `win_glimp.cpp`, input, the wndproc, the sampling profiler `win_profiler.cpp`).

**Threading and frame loop.**
- With `com_smp 1` (the default), `idGameThread` (`framework/Common_local.h`) runs game logic and the renderer frontend, while the main thread runs the render backend for the previous frame.
- Game tics are fixed-rate at `com_engineHz` (default 60). The frame loop runs a catch-up of several tics per frame when it falls behind, so one slow tic snowballs into visible hitches.
- Parallel work goes through `idParallelJobList` (`idlib/ParallelJobList.h`).
- `common->Printf` from non-main threads is queued and flushed by the main thread.
- An engine error inside a job (`idParallelJobList::InJob()`) only throws its message; the thread that waits for the list makes a fatal error of it (`... (in a job)`). Unwinding a job thread would end the process without a word.

**SIMD paths are disabled.** `neo/idlib/sys/sys_defines.h` doesn't define `ID_WIN_X86_SSE*_INTRIN`, so idLib's `#ifdef ID_WIN_X86_SSE*_INTRIN` branches (LCP, MatX, etc.) compile to their generic C++ fallbacks. The shipped game used SSE, so these generic paths are barely tested and have hidden real bugs. For example, a wrong unrolled loop in `DotProduct_SIMD` in `idlib/math/Lcp.cpp` produced NaN ragdolls, and NaN bounds then made every collision query test the whole world. `idSIMD_SSE` in `Simd_SSE.cpp` still uses intrinsics unconditionally.

**Physics notes.**
- `idPhysics_AF` (`d3xp/physics/Physics_AF.cpp`) builds row-padded `idMatX` systems with `MATX_ALLOCA`, whose padding is uninitialized, and solves them with `idLCP`.
- `idLCP::Solve` leaves the matrix columns permuted, so callers must not reuse the matrix.
- `af_checkInvalid 1` (the default) reports the first solver stage that produced a non-finite AF state.

## Direct3D 12

- The renderer is Direct3D 12 (`neo/renderer/D3D12/`), the only backend: `R_InitBackend` makes it with `R_CreateRenderBackend`. The `r_renderApi` of an old config is an unknown cvar now. It needs a DX12 Ultimate GPU: feature level 12_2, shader model 6.6 and resource binding tier 3 (Radeon RX 6000, GeForce RTX 20, Intel Arc or newer); on another the Init fails, and the fatal error names what the GPU has (`idRenderBackend::Init` returns the reason). Windows' own DLLs (`d3d12.dll` and `dxgi.dll`) are loaded at its Init only from System32, never linked and never from the exe's folder, so a planted copy is never picked up. On 64-bit Windows System32 is the folder of the 64-bit DLLs (the name is historical; the 32-bit ones live in SysWOW64). DLLs that ship with the exe (FFmpeg, DXC's `dxcompiler.dll` and `dxil.dll`, which signs the DXIL) load only from its folder. The runtime is the Agility SDK's `D3D12\D3D12Core.dll` when it is newer than the system's (`d3d12_Agility.cpp` exports `D3D12SDKVersion` and `D3D12SDKPath`); the startup line `d3d12: adapter ...` names the runtime and the shader model.
- Ask the device through `D3D12_CheckFeature` (`CheckFeatureSupport1` with the SDK version): the Agility debug layer warns at every plain `CheckFeatureSupport` (#989). `D3D12_DxcCompile` (`d3d12_Dxc.h`) compiles HLSL 2021 with DXC.
- The render programs are HLSL 2021 in `base/shaders`, compiled by DXC at run time (`d3d12_HlslCompiler.h`): `<name>.vfp` is `shaders/<name>.hlsl`, `VSMain` as `vs_6_6`, `PSMain` as `ps_6_6`; `<name>_skinned` is the same file with `SKINNED=1`. A stage's parms are the `float4` members of its cbuffer (b0 VS, b1 PS) named like `renderParm_t`, in that order; b2 is the joint block. Textures and samplers are bindless: `TEXTURE2D`, `TEXTURECUBE` and `SAMPLER` of `include/bindless.hlsli` read `ResourceDescriptorHeap`/`SamplerDescriptorHeap` at the indices of b3 (26 root constants: 8 2D views, 8 cube views, 8 samplers, then `colorFlags` and `preExposure`), and the masks are the b3 slots a stage reads; a `register( t# )` or `s#` binding is refused, and so is a render program that reads `sampler<n>` without a texture at n (a draw fills a slot's sampler from its texture, as GL's units did). The preprocess runs with the stage's `-T`, so `__SHADER_TARGET_STAGE` works. The backend's own passes are `shaders/internal/*.hlsl`. Copy `base/shaders` into the game install with the exe (`run-vdemos.ps1` does); a missing internal file is fatal.
- The ports are one to one: the same math in the same order as id's programs (`base/renderprogs`, removed with the converter; `git show c6f9b6b:base/renderprogs/<name>.vertex` has them), with GL's conventions (`include/common.hlsli` lists them: the clip position `precise` through `GLClipToD3D`, `COLOR0`/`COLOR1` outputs saturated, `FragCoord`). `Hlsl_ProgramInterfaces` holds every program to the parms, masks, joints and tracing of `neo/tests/d3d12_golden/renderProgInfo.txt`: id's programs as GL reported them, ours as they were reviewed (a wanted change of one is a change of its line); `Hlsl_SourcesCompile` allows no DXC warning.
- The programs are a table in C++ (`renderer/RenderProgTable.cpp`): name, builtin, skinned variant, vertex only, optional skinning, of our own, tracing. Shared code takes the builtins and the joint flags from it, D3D12 which stages exist; a name the table lacks fails to link as it did in GL (an Error), a stage it lists but `base/shaders` lacks is a warning and no shader. The GLSL of the retail packs lacks `heatHaze`, `colorProcess` and the vertex stage of `heatHazeWithMask`: on the removed OpenGL backend these failed to link (the first load of `_x7_heathaze`'s map), on D3D12 they draw. `Hlsl_ProgramTable` holds the table to `base/shaders` and to `renderProgInfo.txt`. `d3d12_compileAll` compiles every stage of `base/shaders`, `internal/` included.
- At Init the backend builds every stage of the program table and its internal passes in batches (`idD3D12HlslCompiler::BuildAll`, `idD3D12ShaderLibrary::Prebuild`), and `CreateStage` takes the result; the first frame drops what Init did not ask for (a stage made later is built again from the cache, so an edited file counts). Preprocessing, the cache and the reflection run on the main thread, the DXC runs the cache lacks on worker threads at once (`r_d3d12ShaderThreads`, 0 = one per hardware thread, 1 = one after another), one per distinct text; the shutdown line `d3d12 shaders: compiled ...` gives the time. Code on those threads must not call `va` (shared buffers) or `fileSystem`.
- The DXIL of every stage lives in `fs_savepath/base/shaders/cache` (`r_d3d12ShaderCache 1`), keyed by the preprocessed text, so an edited include rebuilds what uses it. The PSO caches live in `fs_savepath/base/renderprogs/dxbc`: the PSO keys of earlier runs (`pipelines.journal`, made again when their program is created at Init or a level load) and the driver's pipeline library (`pipelines.bin`, `r_d3d12PipelineLibrary 1`). Delete both folders for a cold start; a stale or broken file is rebuilt on its own.
- Descriptors: the views live in one non-visible SRV pool whose every slot is copied at the same index into a shader-visible heap of 2^17; a slot a submitted list may read is never written again (a resized scene surface gets a new one, the old one goes through the graveyard). The sampler heap (2048, `idD3D12SamplerHeap`) holds one slot per sampler state that something holds (`Acquire`/`Release`: a texture its own, the fallback and the internal passes theirs for good); a slot nobody holds goes through the graveyard and is reused after it, so new `r_lodBias` values never fill the heap. An unbound slot that a program samples reads the black fallback view. The root signature is b0, b1, b2 as root CBVs and b3 and b4 as constants (41 DWORDs), with both heaps directly indexed.
- Render graph (`d3d12_RenderGraph.h`), for the post-process chain: passes (raster, compute, copy) declare what they read and write per mip; `Execute` culls the passes whose results nothing reads, takes transient textures and buffers from `idD3D12ResourcePool` (by description; a resource unused for 30 frames is freed) and transitions every subresource before its pass, with a UAV barrier between two UAV accesses. Imported resources (the scene's) keep their own state. Compute stages are `CSMain` as `cs_6_6`, backend passes only, on their own root signature (b0 a root CBV, b1 8 root constants) and read every resource through `ResourceDescriptorHeap`: a `t#`/`u#` binding is refused.
- HDR scene (`d3d12_Hdr.h`), `r_hdr 1` (the default) where `caps.hdrScene`: shared code finds the main view (`RB_FindHdrMainView`: the last drawing `RC_DRAW_VIEW_3D` that is no subview and not marked `notMainView`, before the first drawing GUI view; per eye in stereo) and calls `BeginHdrScene` before the command loop, `ResolveHdrScene` at the end of that view's `RB_DrawView` (after the motion blur) and the idempotent `EndHdrScene`. In between, draws, clears and colour copies go to an RGBA16F scene. In each view the lights add there in linear; the passes after them (`RB_DrawShaderPasses` and `RB_FogAllLights`: unlit stages, translucent surfaces, in-world GUIs, fog and blend lights) blend in gamma, as id's content was made for: `SetHdrSceneGamma` turns the view's rectangle into its sRGB encoding (extended above 1) and back (`internal/hdrEncode.hlsl`, through a copy, per sample under MSAA; `r_hdrGammaBlend 0` blends them in linear, which washes out alpha-blended fog and GUIs). The resolve tonemaps the scene into the view's rectangle of the RGBA8 output, and the debug tools, `RC_POST_PROCESS`, the FX and all 2D draw there as before. No main view (menus, loading, PDA, editor previews) is an LDR frame; `r_hdr 0` gives the frames of before, up to the compiler's last bit on single pixels.
- Colours (`include/colorspace.hlsli`, `colorFlags` bit 8 the linear phase, bit 10 the gamma phase): in the linear phase every 8-bit texture of a colour slot, every colour parm (`RB_ColorParm`) and the vertex colour before its inverse are decoded sRGB to linear (`DecodeColor`, `SceneColor`), normals and densities are not; gui and bink compute in gamma as id did and decode at the end. In the gamma phase nothing is decoded. A copy of the HDR scene is an RGBA16F surface (`d3d12TextureSurface_t::linear`, `colorFlags` bits 0-7), which `SceneColor( c, slot )` divides by `preExposure`. Every PS returns `SceneOutput`: max 0, exposed by `preExposure` when the blend adds radiance (bit 9; not when the source colour is a factor, `DST_COLOR`/`SRC_COLOR` blends), alpha saturated. In the float target a blend with dst alpha ONE takes the alpha by MAX, so `DST_ALPHA` stages still see 0..1. What a pass renders into is a byte of its own in the PSO key (`pipelineKey_t::target`, `d3d12TargetId_t`: the output's two views, the HDR scene, the G-buffer, the scene with the light target, each per sample count; 20 ids).
- The resolve is a render graph: a Karis-weighted MSAA resolve (`internal/hdrResolve.hlsl`), the eye adaptation, the bloom, the local exposure, the Combine LUT (`internal/combineLut.hlsl`, 32^3 RGBA16F in log2 coordinates, rebuilt only when its parms change: white balance, grading, the curve) and the tonemap (`internal/tonemap.hlsl`: EyeAdaptation's exposure / preExposure, the LUT, a dither). The backend reads no cvar: the settings come in `postProcessSettings_t` (`renderer/PostProcessSettings.h`, from `R_DefaultPostProcessSettings`): `r_hdrTonemap` (0 clamp, 1 AgX, 2 a film curve in ACEScg; each scaled by `d3d12Lut::CurveScale` so that the demos keep the mean brightness of the LDR frames, so a switch of curve changes no exposure), `r_hdrAgxLook` (0 base, the default; 1 punchy: deep blacks and saturated light; both archived and set in the game by Settings > System > Tonemapping and Color Look, dimmed without an HDR scene, the look also off AgX), `r_hdrExposureCompensation` (EV), `r_hdrWhiteTemp`/`Tint`, `r_hdrSaturation`, `r_hdrContrast`, `r_hdrDither`, `r_hdrGammaBlend`, `r_hdrDebug 1` (the eye adaptation once a second), `2` (the phase of every frame) or `3` (the eye adaptation of every frame with the view's time, to compare two runs line by line), `r_hdrVisualize 1` (the histogram and the EVs over the frame), `2` (false colour in stops around mid grey), `3` (the bloom alone) or `4` (the local exposure: its base, red where it darkens, blue where it brightens). `MRB_HDR` times it in `r_pix`.
- Eye adaptation (`internal/exposureHistogram.hlsl`, `exposureAdapt.hlsl`): 64 bins of EV100 from `r_hdrHistogramMinEV` to `MaxEV`, one value per 2x2 pixels of the viewport, weighted toward its centre by `r_hdrMeteringMask` (darker than the range does not count, black shadows among it). The mean between `r_hdrLowPercent` and `r_hdrHighPercent` of the weight, in steps of 1/16 EV and clamped to `r_hdrMinEV100`..`MaxEV100`, is the target (the steps keep a driver flake's block, about 1e-5 EV, out of the adapted value and the frames after it); the adapted EV100 moves toward it by `1 - 2^(-seconds * r_hdrSpeedUp/Down)` of the main view's game time (`RB_HdrExposureStep`: at once on a new view or viewport size, after a level load or a resize; not while a screenshot is taken, nor for the second eye). The exposure is `2^(r_hdrExposureCompensation + r_hdrAutoExposureBias - EV100) / 1.2`; the defaults (bias -2.5, EV100 -3.25..-1.25) keep the demos at the mean brightness of the LDR frames (`analyze.py --luma`: median ratio 1.03) and brighten a dark scene by 0.5 EV at most, so Doom 3 stays dark. `r_hdrAutoExposure 0` is `2^compensation`. The histogram and EyeAdaptation are buffers of the context; the CPU reads EyeAdaptation's copy after Present's wait and draws the next frame with that exposure as preExposure, so two runs give the same frames. A reset (level load, resize) drops the readbacks: until the next one the frames are drawn with the manual exposure, as after Init, because the gamma-phase blends depend on preExposure; so a demo gives the same frames whatever ran before it.
- Bloom (`internal/bloomDownsample.hlsl`, `bloomBlur.hlsl`, `d3d12Bloom` in `d3d12_Hdr.h`): `r_hdrBloomQuality` + 1 levels (0 none) of an RGBA16F mip chain from half the viewport down, the first by a 13-tap downsample with Karis weights, each next one from the last. Per level, smallest first, a Gaussian in compute: X, then Y times the level's tint plus the smaller level's sum upsampled. It reaches the level's size (`postProcessSettings_t::bloomSizes`, 0.3 .. 64) times `r_hdrBloomSizeScale` percent of the viewport's width. The tints are scaled to a luma sum of 1 and the tonemap lerps the scene toward the sum by `r_hdrBloomIntensity`: a flat field stays as it is, and the eye adaptation's calibration holds. Not R11G11B10: its stores round toward zero, -0.8 % each. From 4x4 down, the taps clamped at the edges move a centred field's weight to the edge texels (`BloomDownsampleRef` in the tests).
- Local exposure (`internal/localExposureGrid.hlsl`, `localExposureBlur.hlsl`, `d3d12LocalExposure` in `d3d12_Hdr.h`): a bilateral grid of 64x64-pixel tiles and 32 bins of log2 luminance over the histogram's range, a Texture3D of ( sum, count ) summed in groupshared integers (fixed point, so the order of the atomics changes nothing), blurred 5x5x3; the tiles' totals blurred by a Gaussian of `r_hdrLocalBlurredKernel` percent of the width are the blurred luminance. The tonemap slices the grid at the pixel's luminance, lerps toward the blurred luminance by `r_hdrLocalBlurredBlend`, scales that base around mid grey by `r_hdrLocalHighlightContrast` / `r_hdrLocalShadowContrast` and the pixel's detail around it by `r_hdrLocalDetail`. The defaults compress the highlights (0.8) and keep the shadows (1); all 1 or `r_hdrLocalExposure 0` adds no pass and gives the frames without it.
- Ray tracing (`r_rayTracing 1`, archived; Settings > System > Ray Tracing, dimmed where `idRenderSystem::HasRayTracing` is false: no HDR scene or a GPU without `caps.rayTracing`): the HDR main view traces its shadows, one bounce of indirect light with the emissive surfaces and glossy reflections (`r_rtShadows`, `r_rtIndirect`, `r_rtReflections`, all 1; below). `0` traces nothing, `r_rtDebug` and `r_rtStats` included: no GPU scene, no G-buffer but for `r_gbufferDebug`, stencil shadows, the frames of before. `R_DefaultRayTracingSettings` reads it each frame, so the switch needs no restart: the GPU scene goes on from what it held, the history starts again (`_xc_rt_switch` flips it on 01_camera). Calibrated at `r_rtIndirectScale`, `r_rtEmissiveScale` and `r_rtFillLightScale` 1: the demos' mean brightness is 1.05 (median of the frames; 0.995-1.13 per demo) of the frames without it, and Doom 3 stays dark; `r_rtFillLightScale 0.5` left hell and delta darker than before. Cost on an RX 7900 XTX (`r_pix`, median GPU ms of the back end's frame, against `r_rayTracing 0`): at 1280x720 1.5-2.5 against 0.3-1.2 (the ray traced passes 0.95-1.5, the scene 0.1-0.25, the traced interactions 0.2-0.6 more than the stencil ones); at 3840x2160 12.4-18.4 against 1.2-2.7 (the passes 9.6-13.6, the interactions 4.9-7.0), where it is the frame (`research/perf.md`).
- Thin G-buffer (R14 of `RenderBackend.h`, `renderer/RayTracingSettings.h`), the input of the ray traced passes: in the HDR main view, after the depth pass, `RB_FillGBuffer` (`tr_backend_draw.cpp`, `MRB_GBUFFER`) draws the opaque surfaces again with `gbuffer`/`gbuffer_skinned` (rows of the program table of our own, made after id's), depth EQUAL without a depth write (a perforated surface once per polygon offset of the alpha-tested stages the depth pass drew: a burning monster's two), into four targets of the scene's size and samples (`d3d12TargetId_t::GBuffer`): the octahedral world normal (RG16 SNORM), F0 and roughness (RGBA8 sRGB: the first specular stage times its colour, 0 for the weapon, GUIs and subviews; the gloss is sqrt( F0 luminance ) × `r_gbufferGloss`), the motion in pixels (RG16F, GL's +y up) against each draw's previous MVP, and the albedo (RGBA8 sRGB: the first diffuse stage times its colour, as an interaction takes it but without the light and the vertex colour, black without a diffuse stage; its alpha says what was drawn: 0 nothing, 1 a surface, 0.5 one under the weapon's depth hack, whose clip z is a quarter of the true one). An MD5 uploads its previous joints right after the current ones in the same joint block (`R_JointMotionLayout`, `rpJointMotion`; 136 joints fill gbuffer_skinned's `JOINT_VECTORS 816`); `idRenderEntityLocal::motionMatrix` keeps the model matrix of the frame before, so a still entity under a still camera moves exactly 0. Nothing of it runs while no consumer asks (`viewDef_t::rayTracing.gbuffer`): the frames are then those without it. `r_gbufferDebug` 1-5 shows the normal, F0, roughness, motion or albedo after the resolve (`_x9_gbuffer`); its raw view shows the AMD depth-tile flake as black 4x2 blocks along edges, in a few frames per demo. `_xb_gbuffer_burn` burns an imp and a wraith in the normals view.
- Light target (R16 of `RenderBackend.h`), for the traced lights: between `BeginTracedLights( rect )` and `EndTracedLights()`, in the HDR scene's linear phase, a draw's first colour output goes to the scene and its second to a second RGBA16F surface of the scene's size and samples (`idD3D12SceneTarget::Lights`, made at the first bracket, cleared to zero inside `rect`), both through the draw's one blend. Only programs with two outputs draw there and nothing clears. An internal pipeline replaces, adds or multiplies (`d3d12PassBlend_t`).
- Render programs that trace (R17 of `RenderBackend.h`; `traces` in the program table: `interaction_rt` and `interaction_rt_skinned`, rows of our own, which the traced lights draw with): the pixel stage includes `include/rtDraw.hlsli`, whose cbuffer at b4 is 9 root constants (`d3d12TraceResources_t`: the heap indices of the TLAS, the records, the instance table, the static vertices and indexes, the skinned vertices, the noise and a linear sampler, then flags), and traces with the inline `RayQuery` of `include/raytracing.hlsli`. The compiler refuses b4 in any other stage (`hlslParms_t::TRACING`, from `D3D12_ProgramParms`) and checks its layout as it does b3's. The draw recorder asks its trace source for every draw of such a program (`idD3D12RtPasses::DrawResources`: the transitions of the scene's buffers, again in every list since they decay, and the walk of `MakeTexturesReadable` only when the scene or `idD3D12TextureStore::StateChanges()` moved) and sets b4 when it differs; all zero (`rtFlags` bit 0 clear: nothing built, an update refused) means no ray. A staged buffer has one read state, vertex or index buffer plus ALL_SHADER_RESOURCE, so a draw and a ray read the static buffers in one list. `interaction_rt` is `interaction` (both are `include/interaction.hlsli`: the same colour into the scene) plus a shadow ray from the pixel's world position (the rows of `rpModelMatrix`, at the centroid under MSAA, off the surface by 0.02 plus a tenth of the pixel's footprint on the side the eye sees; toward a point behind the surface it comes back through the pixel's own point) toward a point of the light's disk (`rpRtLight`: world origin and radius; `rpRtShadow`: the casters' mask and the noise index; a surface that faces the light takes a point behind its own plane from across the disk), ending a radius short of it; where a caster stops it the colour also goes to the light target. The noise (`include/rtNoise.hlsli`) is a 64x64 blue-noise texture of two channels (`renderer/BlueNoise.h`, written by `tools/rt/make_bluenoise.py`, the same bytes on every run: change the script, never its output), shifted by the R2 sequence of the index in integers. A ray that needs several pairs (its direction, a light, a point of the light's disk) takes each with a step of its own (`RtNoise( ..., pair )`: the plastic number's, then square roots of primes): with one step the pairs move together, and what depends on two of them at once keeps an error at any number of frames (grain that `r_rtReference` never lost). `Warp_RtDraw`/`Gpu_RtDraw` draw a floor under a local and a global caster through the recorder: hard and soft shadows, the masks, nothing to trace, a submit between two draws.
- Traced shadows (`r_rtShadows`, 1 by default; needs `r_useGPUSkinning 1`): `RB_UpdateGpuScene` says whether the frame may trace (the update applied, `gpuSceneStats_t::traceable`, and no BLAS that the last full update could not build still waits, `gpuSceneStats_t::lacking`; after 60 gathers `gpuSceneSettle_t` gives up with a warning, and those instances cast nothing until they are built, as one that joins a delta does), and `backEnd.tracedShadows` then holds for the HDR main view; any other frame or view keeps its stencil shadows. Once a frame has traced a world's main view, the front end makes no shadow volumes for the lights that view traces (`rtShadowSettings_t::volumes`, set in `RenderScene` from `tr.tracedScene`: the scene and update the back end's last frame traced, `rtShadowLatch_t`, copied in `SwapCommandBuffers_FinishCommandBuffers` so that it is the same value whatever the threads' timing; after a full update not before the back end traced that one): no shadow surfaces and no prelight volumes, while a shadow-only MD5 still gets its joints uploaded (the GPU scene takes it by them). Subviews and a view drawn for the main one (`RenderScene( view, true )`: the portal sky's) keep their volumes (`KeepStencil`), and so does a second view of a world in a frame or one after a GUI view of the frame that draws (`rtMainViewForecast_t`: the wipe at a level's end draws the game twice in one frame). The front end marks all of these (`viewDef_t::notMainView`) and `RB_FindHdrMainView` passes them over, so the first view stays the main one; a marked view after it is drawn into the output as an LDR view and gathers nothing. A frame that then cannot trace (a refused update) draws its lights without a ray and keeps the shadows its history holds (`backEnd.tracedHeld`, `rtView_t::held`; without a history it is lit whole); the views two frames on have their volumes again. `r_rtShadowVolumes 1` makes the volumes all the same (the frames are the same bytes, a frame that cannot trace draws them: what they cost the front end), and `r_rtStats 1` prints `rt shadows: frames, traced, without volumes, held` once a second, plus a line for every frame that is not traced without volumes (the first two of a level, a held one). A view that traces also leaves out a shadow-casting light whose area is not connected (`AddAreaViewLights`), as it always did the lights without shadows: the GPU scene holds none of that area's walls, so light through the window of a closed door is lost. `RB_DrawInteractions` first draws, in one bracket of the light target (`RB_DrawTracedLights`), the opaque interactions of every light that casts shadows (no ambient, fog or blend light) with `interaction_rt`, depth EQUAL and no stencil, under the light's scissor and depth bounds: the local ones (`noSelfShadow`) with the mask `MASK_SHADOW_GLOBAL`, the others with `MASK_SHADOW`, the noise index 97 times the light's index in its world (`viewLight_t::lightIndex`: no other light of the view's list changes it), plus the view's sequence when the shadows keep a history. `ResolveTracedShadows` (`idD3D12RtPasses::Shadows`, raster passes of the graph, the filter of the next point between them) then stores per pixel and channel what the shadows leave of the lights, ( scene - light target ) / scene (`internal/rtShadowRatio.hlsl`: the difference first, so all taken is exactly 0 and nothing taken exactly 1; a channel no light reaches takes the others' luminance-weighted part; alpha the unshadowed luminance; over the pixel's samples under MSAA), and multiplies the scene by it (`rtShadowApply.hlsl`). The lights without shadows and all translucent interactions follow as before. `r_rtDebug 6` shows the stored part in place of the lights, blue where no traced light reaches. A shadow ray follows the stencil volumes, which come from the triangles that face away from the light: `RtOccluded` culls back faces, and the ray starts on the side of the surface the eye sees, so a surface with the light behind it shadows itself, as a volume's cap does (a light inside a closed mesh, a fireball in a monster's hand, stays shadowed; the triangles of a mesh that face away from the light stay dark, faceted as id's). With `r_rtLightSize 0` the frames are the stencil ones but for the edges; expected differences: alpha-tested casters cast their holes, a projected light's rays pass the space before `light_start`, `suppressShadowInLightID` is no ray mask, what is outside the GPU scene casts nothing, and a hull that draws nothing (`textures/common/shadow`) casts also where the stencil shadows never drew it: as a part of an entity (the cacodemon's shadows its mouth and the hands under it), and from a light that moves. A light with a size gives a grainy penumbra without the filter, and a lamp closer than its radius to a wall loses the part of its disk behind that wall for the surfaces beside it. A dim traced light inside a much brighter one's shadow is quantized by the bright sum's half-float step, about 1e-3 of it. `Warp_RtShadows`/`Gpu_RtShadows` resolve one and two lights, a local surface, a noshadows quad, one that faces the light, the floor's own shadow of a light behind it, the shown picture and a light of radius 6 over 64 noise indices against the hidden part of its disk (`idTestTracedFloor`, which `RtDraw` shares).
- History and the shadows' filter (R18 of `RenderBackend.h`, `D3D12/d3d12_RtHistory.h`, `include/rtDenoise.hlsli`): shared code numbers the HDR main view's frames per eye (`RB_BeginMainViewHistory`, `backEnd.viewEpoch` and `viewSequence`: a view follows the one before when the viewID, the size and the frame number plus 1 agree and the time did not go back; anything else starts an epoch at sequence 0) and `rtView_t` carries both with this frame's and the previous world-to-clip matrix. A pass reads only what sequence - 1 of its epoch stored. A screenshot reads the history and stores nothing (`rtView_t::store`), so the frame after it is the one without it. A frame that traced nothing (`rtView_t::held`, the traced shadows' frame without volumes) takes what the history holds of a pixel in place of the frame's value, uncut and without counting a frame; a pixel without a history holds no value there. `idD3D12RtHistory` holds, per eye and slot, a pair of surfaces with the epoch and sequence each was written at (the same sequence again reads and writes the same two: the second eye's no-op, a view drawn twice); the context drops it at a resize, a level load and the shutdown. `rt guides` (compute, `internal/rtGuides.hlsl`, sample 0 under MSAA) packs what tells two surfaces apart into an R32_UINT, kept for the next frame: the G-buffer's normal in 2 x 7 bits, log2 of the clip w in 16, drawn, and bridged (a hole of the G-buffer keeps the guide and the history of the frame before, once). Its two transients say where the pixel was (the G-buffer's motion, the previous clip w over this one) and how 1 / w changes per pixel, which is linear over a plane on the screen. `rt shadow temporal` (`internal/rtTemporal.hlsl`) averages what the shadows leave over at most `r_rtShadowHistory` (16) frames: four bilinear taps of the frame before, each only from the pixel's surface (the expected w within 2 % plus the slope, the bumped normals within 53 degrees), none where the unshadowed luminance left the taps' range by a quarter (a light went on, off or strobes), and beside it the luminance squared for the variance. The taps mix their variances, not their second moments (a gradient between two texels is no noise), and a tap of 4 frames or more that is farther from the frame's value than 4 deviations of its noise, and twice as far as the nearest tap, lies across an edge and is left out: a moving eye mixes no hard edge, while a penumbra's lone sample, which no tap is near, keeps all four. A pixel no traced light reaches (the resolve's alpha is 0: a bump that faces away from the light, the floor beyond it) holds a part of nothing: it gets no history, no neighbour and no later frame takes it, and its variance of -1 tells the passes so (taken, it lightened the shadowed bumps beside it on a monster's back). An average of 4 frames or more that lies outside the range of the pixel's 3x3 or 5x5 neighbours of the same surface in this frame, by more than two deviations of the difference between its mean over its frames and the mean of that many neighbours, is cut to the range and, by as much (wholly from a quarter on), becomes the frame's value with the neighbours' variance and 3 frames: a hard shadow that slides an eighth of a pixel to a whole one a frame trails one pixel. A store into a half float drops the bits below its last (WARP and AMD alike), so the filters round to the nearest half themselves (`RtHalf`), sum their taps as differences to one of them and step an average by at least its last bit (`RtAverage`): the average of a constant becomes that constant to the bit, and what a driver flake left in a history ends. `rt shadow atrous 1..n` (`internal/rtAtrous.hlsl`, `r_rtShadowPasses` 3, strides 1, 2, 4) are 5x5 B3 splines whose taps count by the plane, the normal and the luminance within four standard deviations: where the history holds no noise (a point light's shadow, an umbra, a lit floor) nothing is blurred. Fewer than 4 frames tell no variance; the pixel's 5x5 neighbours do then, so a new or disoccluded pixel is blurred across a shadow's edge for 3 frames, and always with `r_rtHistory 0` (the spatial filter alone on the same noise every frame: two runs give the same bytes whatever came before). `r_rtHistory 0` with `r_rtShadowPasses 0` is the unfiltered resolve. `r_rtReference 1` is a plain average of up to 4096 frames in RGBA32F without a pass, a cut or a side, for a still camera. The history is 32 bytes per pixel and eye (118 MB at 2560x1440), made at the first traced frame. Measured on the demos: on the lab's still stops the penumbra's RMS error against `r_rtReference` is 35 of 255 with one ray, 7.8 with the passes alone and 3.5 with the history; with point lights 0.01 % (lab, `01_camera`) to 0.2 % (`04_lighting`) of a frame is off by more than 12 against the one-ray frame, thin lines along edges, 0.6 % under the lab's dolly, where a fast eye still softens a hard edge by a pixel or two. A lit line thinner than a pixel pair (between a grate's bars) has no tap of its own side and softens too. Two runs with a history differ by the driver's lone blocks only, in as few frames as without ray tracing, each for its one frame. What the cut cannot tell, a history inside its neighbours' range that is still of another signal (at 60 fps a soft shadow that moves many pixels a frame, the lab's rotor, leaves its umbra inside the new penumbra, whose range holds every value), the temporal gradient does: `rt shadow gradient` (`internal/rtGradient.hlsl`, a texel per tile of 8x8 pixels) sums how far the frame's values lie from the histories of the same pixels and the noise that explains a difference; where the tiles around a pixel lie farther apart than that, its history is shortened by as much, down to none, which costs noise for some frames and never a wrong value. A pixel beside a hard edge of the history does not vote: there the cut answers and keeps the edge sharp. With it the rotor's shadow no longer lags at 60 fps (a little blockier along some edges), and at 240 fps its penumbra is a little grainier. The demos draw 4 frames per tic (`vdemo_fps 240`), so their histories hold a quarter of the game time a 60 fps player's do: judge the look with `+set vdemo_fps 60`. `Warp_RtHistory`/`Gpu_RtHistory` draw the traced floor with perspective, depth and a G-buffer over frames: the error against the hidden part of the light's disk after 1, 4 and 16 frames and with the passes, a hard shadow kept sharp, also under an eye that glides a quarter of a pixel a frame, one that slides (nothing 2 pixels off its edges), one beside a floor no light reaches, one moved 4 pixels (nothing off its edges a frame later, a lone frame's bytes 80 frames later), a soft one that moves 8 pixels a frame (its penumbra about a first frame's, no pixel off by more than half), a moved eye, a quad taken away, a light halved and one a tenth dimmer, no history after two pasts, a sequence drawn twice, a screenshot, the reference.
- Indirect light (R19 of `RenderBackend.h`, `internal/rtIndirect.hlsl`, `include/rtBounce.hlsli`), `r_rtIndirect` (1 by default; it needs no `r_rtShadows`): after the reflections and before the gamma phase (`DrawRayTracedIndirect`), one bounce for the HDR main view on a grid of a texel per stride pixels a side (`r_rtIndirectResolution` 0.5: every second pixel; a texel is its block's first pixel). `rt guides` of that grid hold the plane the depth gives (`RtDepthNormal` of `include/rtView.hlsli`), not the bumped normal, so the bumps of a wall share one signal. `rt indirect` sends a ray by the cosine about that plane, up to `r_rtIndirectDistance`; the hit is lit by `RtShadeSampled` (`include/rtLighting.hlsli`): of the lights that reach it one, picked by what it adds unshadowed (one number, a reservoir of one) and scaled to the sum, with one ray toward a point of its disk (`RtDiskOccluded`: also for a light that casts no stencil shadow, the flashlight, whose bounce must not come through walls; not for an ambient light), without specular, plus the emissive stage times `r_rtEmissiveScale`. So the emissive surfaces light through these rays; no list of them exists. A ray brings at most `r_rtIndirectClamp` (8) times the exposed scene's white (in the lab's emissive room 0, 2, 8 and 32 give the same frames but the level's first one: a net for a higher emissive scale and brighter lights). A texel keeps, unexposed (2 x RGBA16F), the mean luminance (Y of YCoCg), that times the rays' directions, the chroma, the luminance squared and its frames. `rt indirect temporal` averages them over at most `r_rtIndirectHistory` (24) frames, its taps tested as the shadows' are (no cut against the neighbours and no gradient: light that changes fades in over the history), `rt indirect atrous 1..n` (`r_rtIndirectPasses` 4) blur over the same surface as far as the variance says (a texel of fewer than 4 frames takes every tap of its surface: after a cut and on a disoccluded strip the light is blurred for 3 frames, where the luminance's weight left a lone bright ray a dot), and `rt indirect upsample` (raster) gives every pixel the texels of its surface among the four around it (among the twelve around those for something thinner than the grid), by its own bumped normal: `RtBounceShare` reads the kept amount and mean direction as an even glow of the half sphere plus light from one direction, exact for either and any mix, and a flat surface takes exactly 1; times the albedo, `r_rtIndirectScale` and preExposure, added to the scene. `r_rtDebug 8` puts it in the scene's place as a white surface takes it. `r_rtFillLightScale` (1, 0..1) dims id's stand-ins for bounced light while the indirect light is on (`R_FillLight`: ambient lights and point lights without shadows; a projected one without shadows is a lamp of its own), in the main view's interactions and for the rays. A frame that cannot trace takes what the history holds; `r_rtHistory 0` and `r_rtReference 1` work as for the shadows. Measured at 1280x720 on an RX 7900 XTX: 0.38-0.42 ms of GPU time on the retail demos and 0.23-0.28 ms in the lab's rooms, about three times that at every pixel; on a still stop the frame lies 1.3-2.1 of 255 (RMS) from `r_rtReference`, 3-5 without a history. Known limits: a surface one pixel wide gets its light only where the grid meets it (a dashed line in `r_rtDebug 8`; `r_rtIndirectResolution 1` traces every pixel); the passes carry a little light across the line of an indirect shadow (under 5 % of the lit side in the test); with the indirect light on the eye adaptation meters what was black before, so a dark room's exposure rises within its 0.5 EV. `Warp_RtIndirect`/`Gpu_RtIndirect` (1 and 4 samples): under an emissive sky the floor takes the sky's light at strides 1, 2 and 4, added, alone, scaled and clamped, a leaning normal its share; a room beside a lit wall against the form factor on the CPU (the means within 3 %), nothing behind a black plate and behind the wall, two lamps their sum; the same bytes without a history whatever came before, for another epoch and after a screenshot; a frame that cannot trace.
- GPU scene (R15 of `RenderBackend.h`, `renderer/GpuScene.h`), what the ray traced passes trace: one `idGpuScene` per render world gathers, after `R_AddModels` of a main view that asks (`viewDef_t::rayTracing.scene`), the entities of its connected areas (static vertex-cache models and the MD5s skinned on the GPU this frame; no translucent or deformed surface, weapon or other view's surface) into a slot per entityDef: a range of 288-byte geometry records (offsets into the static buffers, flags, the bump, diffuse, specular, emissive and alpha textures with their stage matrices and colours), plus the frame's instances (transform, mask, BLAS key, joints; a slot's surfaces are up to eight instances, by side, by the material's `noSelfShadow` and by whether they are drawn, `GpuScene_OrderByGroup`; what only casts, a material without a stage and with `forceShadows`, is `GEO_SHADOW_ONLY` and its instance lacks `MASK_VISIBLE`, so no ray but a shadow ray meets it, and so does every instance of an entity the view suppresses without its shadow, the player's body under `g_showPlayerShadow 1`) and lights, written whole each update into a buffer of their own. A record's parms are the entity's as a draw evaluates them (`R_EntityShaderParms`: a light's model follows its light's `referenceShader`). A record goes out only when it differs from what the GPU holds. A full update follows the first frame, a level load, a new set of static buffers (`vertexCache.StaticGeneration()`) and a refused update (asked for once, `gpuSceneRecovery_t`: with `com_smp 1` the delta gathered meanwhile is refused too). Every view of a frame that sees other areas gathers again (a portal sky's view comes before the player's) and its update holds every write of the frame so far, after `base`, the last update of the frame before. Only the HDR main view sends (`RB_UpdateGpuScene`, which loads an image no draw has bound yet): the backend applies a full update or one whose writes follow what it holds (`base` <= its sequence < the update's), takes the same one again as a no-op (the second eye), and refuses a gap, another scene or a delta after a SAMPLED texture that a held record views died (`idD3D12TextureStore::SampledDestroyed`; any other texture, a video's, changes nothing); nothing may be traced until the next full one. `idD3D12GpuScene` keeps the records in a DEFAULT buffer with a raw SRV that only grows (a GPU copy into the bigger one) and a CPU copy for the acceleration structures. `r_rtStats 1` builds it and prints `rt scene <id>.<sequence>: instances, geometries, written, capacity, lights, refused` once a second, then what the acceleration structures made of it, and for every refused update why (`gpuSceneRefusal_t`).
- Acceleration structures (`D3D12/d3d12_RayTracing.h`), built as render graph passes after each applied update (the no-op of the second eye builds nothing): `rt skin` (`internal/rtSkin.hlsl` skins every skinned instance into a buffer of the frame in idDrawVert's layout, normal and tangent normalized), `rt blas` (new static BLAS with PREFER_FAST_TRACE, every skinned one with PREFER_FAST_BUILD), `rt blas compact`, `rt tlas` (InstanceID the instance's first geometry record, its mask) and `rt blas sizes`. A static BLAS is one per BLAS key, checked against its geometries (another model under a held key waits), kept 600 builds after its last instance and dropped with the static generation; after a full update a build makes every one the scene lacks, so that frame traces all its casters, in batches of 32 MB of scratch that take the same bytes one after another (a UAV barrier between two); after a delta new ones up to 32 MB, the instances of the rest wait. Compacted sizes are read once `WaitedFence()` passes their list, never by polling, so two runs record the same commands; WARP's compacted sizes are its built ones. The instance table (`d3d12RtInstance_t`: first geometry, count, skinned offset, scene instance) is a raw SRV by InstanceIndex. The graph puts a UAV barrier after every imported structure it wrote last, so a later graph of the list reads it built. A WRL `ComPtr`'s `&` releases what it holds: take its address with `std::addressof`.
- Ray traced debug views (`D3D12/d3d12_RtPasses.h`, `internal/rtDebug.hlsl`): `r_rtDebug` (`rtDebug_t`, any value gathers the GPU scene) traces a ray per pixel of the main view against what the last applied update built and draws it over the output after the resolve (`DrawRayTracingDebug`): 1 a colour per instance, 2 the rays against the depth (grey agrees, red misses a drawn surface, blue hits in front of one, yellow a back face), 3 the hit normal, 4 the diffuse colour, 5 the reflections alone, 6 what the traced shadows leave of the traced lights, 7 the length of their history, brightest at `r_rtShadowHistory` frames and black where no traced light reaches or without a history, and 8 the indirect light alone, as a white surface takes it (all four in the scene, before the resolve, so the tonemap shows a full history as mid grey). `MRB_RT_SCENE` (update and builds) and `MRB_RAY_TRACING` time them in `r_pix`. `include/raytracing.hlsli` reads a hit through `ResourceDescriptorHeap` with inline `RayQuery` (`include/ycocg.hlsli` decodes the diffuse); textures live in ALL_SHADER_RESOURCE and `idD3D12GpuScene::MakeTexturesReadable` transitions the records' textures before a trace. The front face is the side Doom 3 draws (`TRIANGLE_FRONT_COUNTERCLOCKWISE`) and the rays cull back faces as the raster does: an instance holds two-sided geometries only and gets `CULL_DISABLE`, or none (an opaque back face never reaches the candidate loop, so only its instance can cull it). Perforated geometry is alpha-tested as the depth pass tests it: the GPU scene leaves out a surface whose stages are all conditioned off (a dead wraith's wings), a perforated one with no enabled alpha-tested stage is opaque, and enabled stages of one image and matrix take the lowest reference (a monster's two burn stages). AMD's driver gives a committed non-opaque hit the candidate's t plus TMin (`Gpu_RtHit`): `RtTrace` starts the query at TMin with a TMin of 0. Mode 2 may show red on the weapon, particles and translucent surfaces that write depth (`textures/glass/glass2`'s heat haze), all outside the GPU scene, and speckle on alpha-tested edges (the samplers differ). `_x8_rtdebug` runs the modes over the gallery, `_xa_rt_portalsky` modes 2 and 4 over `game/mp/d3xpdm4`, the retail map with a portal sky; `Warp_RtHit`/`Gpu_RtHit` hold the hit attributes, the culling, the alpha test and the sides a shadow ray stops at.
- Reflections (R20 of `RenderBackend.h`; `D3D12/d3d12_RtPasses.h`, `internal/rtReflect.hlsl`, `rtReflectTemporal.hlsl`, `rtReflectAtrous.hlsl`, `rtComposite.hlsl`, `include/rtReflection.hlsli`, `include/rtLighting.hlsli`): `r_rtReflections` (1 by default) traces, after `RB_DrawInteractions` and before the gamma phase (`DrawRayTracedReflections`), a ray per pixel of the HDR main view whose G-buffer reflects (F0 above 0, roughness below `r_rtReflectionRoughness` 0.6, faded in over 0.15 below it): from the point the depth gives, off the plane its neighbours hold (`RtDepthNormal`), up to `r_rtReflectionDistance`. `rt reflect` stores what the ray met, before the surface's Fresnel, and how far it went. A pixel smoother than `r_rtReflectionMirror` (0.08), and every pixel with `r_rtReflectionGlossy 0`, is a mirror: its ray leaves about the G-buffer's normal (kept above that plane), the same every frame, with no history and no filter. Its hit is lit as the linear phase lights a pixel (interaction.hlsl's math in the hit's object space, the modifiers decoded as products, ambient lights without specular, vertex colours white, the emissive stage added in linear) by the first `r_rtReflectionLights` lights that reach it. Those are the GPU scene's `gpuSceneLight_t`: every light of the connected areas but fog and blend lights and those whose centre lies in an area that is not connected (behind a closed door: none of that area's walls are in the scene to stop it), one per enabled stage, projection and falloff in world space with the stage matrix baked in. A light has a size: the spawn arg `light_size` is the radius in units of the disk that emits, by default 2 % of the light's reach (the largest `light_radius`, the length of a projected light's `light_target`) within 2..10 units, all times `r_rtLightSize` (0 = points); `R_LightEmitterRadius` gives it to `viewLight_t` and `gpuSceneLight_t`, and a savegame or a render demo does not hold it (idLight reads its spawn arg again). The traced shadows, a bounce and a glossy ray sample the disk; a mirror's shadow rays aim at its centre. Each casts one (`r_rtReflectionShadows`) from the side of the hit that the reflection came to: `RtOccluded` culls back faces, since Doom 3's shadow volumes come from the triangles that face away from the light (a hit on one is in its own shadow), and skips geometry without `GEO_CASTS_SHADOW` (a lamp's noshadows model), which the BLAS therefore holds not opaque. A hit on a `noSelfShadow` material traces only the casters that are not (`RtShadowMask`, mask bit 2 `MASK_SHADOW_GLOBAL`), as the stencil shadows draw the local interactions before the local shadows. A rougher pixel's ray leaves about a facet of its GGX lobe (alpha the roughness squared, the facets drawn as the eye sees them, `RtGgxVisibleNormal`; without the last tenth of the lobe, `RT_REFLECT_LOBE`, whose rays land lobes away as lone dots) and its hit is lit by `RtShadeSampled` as a bounce's is, here with the highlight: one light for all that reach it and a ray toward its disk. `rt reflect temporal` averages the rays over at most `r_rtReflectionHistory` (16) frames. It looks the history up twice, where the surface was (the G-buffer's motion) and where the reflected image was (the point as far behind the surface as the rays went on average, through the previous world-to-clip), and takes the one nearer the mean of the pixel's 5x5 neighbours of this frame; a mean of 4 frames or more outside their range is cut to it as the shadows' is. `rt reflect atrous 1..n` (`r_rtReflectionPasses` 4, strides 1, 2, 4, 8) blur over the same surface and roughness, no farther than the lobe reaches on the screen (`RtReflectLobePixels`: the roughness squared times the rays' reach over the whole path, in pixels) and within four deviations of the luminance: a near mirror's image stays sharp and a rough floor's is as wide as its lobe. `rt composite` (raster) multiplies by Schlick's Fresnel capped by the smoothness, the fade, `r_rtReflectionScale` and preExposure and adds that to SceneColor's RGB; `r_rtDebug 5` puts it in place of the lights' sum. A frame that cannot trace shows what the history holds of the glossy pixels and nothing in a mirror. `r_rtHistory 0` is the passes alone on the same noise every frame; `r_rtReference 1` a plain average that starts again when the eye moves (what a surface reflects depends on where the eye is). The history is 24 bytes per pixel and eye (88 MB at 2560x1440) beside the shadows' guides. Measured at 1280x720 on an RX 7900 XTX: 0.22-0.56 ms of GPU time on the retail demos and 0.3 ms in the gallery and the gloss room, against 0.08-0.25 and 0.1 ms with `r_rtReflectionGlossy 0`; on the gloss room's still stops the floor lies 0.5-0.7 of 255 (RMS) from `r_rtReference`, 1.2-1.9 without a history (mirrors in its place 5-17). With `r_rtReflectionGlossy 0` the frames are the mirrors of before up to 1 of 255 (the radiance is stored as a half before the Fresnel) and a lone pixel on a reflected edge now and then. Known limits: what a reflection shows is lit by the lights and its own emission, by no bounce, so with the indirect light on a mirror's image is darker than the room; a hole of the G-buffer reflects nothing for its frame; a retail material's roughness comes from its specular map's luminance (`r_gbufferGloss`) and varies per texel. `Warp_RtReflection`/`Gpu_RtReflection` run the mirror end to end: a mirror floor under a lit ceiling, a two-sided shadow caster, a noshadows one, an emissive panel, a rough and a black band. `Warp_RtGlossy`/`Gpu_RtGlossy` (the sky also at 4 samples): under an emissive sky every roughness reflects the sky times its Fresnel, in one frame, filtered and in the reference; under a ceiling of an emissive and a black half a rough band shows the part of its lobe that meets the emissive half, which the CPU sums over the facets (a column's mean within 0.03 in the reference, 0.06 after 32 filtered frames); the same bytes for another epoch and after a screenshot; under an eye that moves 4 units a frame the line's image stays where it is (0.99 of its half three pixels beside it; 0.92 with the history looked up only where the surface was); a frame that cannot trace; and under a red and a blue lamp at one place a pixel is as red as it is blue (the noise pairs' own steps).
- `r_debugContext` (read at Init): 1 = the debug layer, whose messages appear in the log as `d3d12 debug: <SEVERITY> ...` (the Agility SDK's `D3D12\d3d12SDKLayers.dll`; the DXGI debug layer still needs the Windows optional feature Graphics Tools); 2 = plus GPU-based validation, several times slower (give the demo scripts `-TimeoutScale 6`); 3 = plus DRED, which prints where the GPU stopped when the device is lost.
- Cvars: `r_d3d12Adapter` (empty = the high-performance GPU, `warp`, or an index), `r_d3d12ShaderThreads`, `r_d3d12Stats 1` (draws, PSOs, uploads, submits, waits and GPU ms once a second, and a `com_showFPS` line), `r_d3d12SubmitDraws` (256), `r_d3d12FrameBuffers` (0: the per-frame vertex cache stays in UPLOAD heaps), `r_d3d12ShowImage <texture>`, `r_d3d12CaptureBackBuffer 1`, `r_d3d12CheckImages 1`. Commands: `d3d12_compileAll`, `d3d12_checkImages`, `d3d12_removeDevice`.
- `d3d12Tests` (`neo/tests/d3d12_tests.cpp`, in ctest) runs the backend's parts without a window, on a WARP device with the debug layer (WARP 1.0.22 of the WARP package: the system's has no feature level 12_2; the parts a driver could get wrong also on the GPU), DXC (`Dxc_Compile`; `Warp_DxcBindless` and `Gpu_DxcBindless` draw through `ResourceDescriptorHeap` on SM 6.6) and `base/shaders` (`Hlsl_Bindless` for the masks and the refused registers, `Hlsl_Entries`, `Hlsl_SourcesCompile`, `Hlsl_ProgramInterfaces`, read from the repo; the pipeline, raster and draw recorder tests draw with its programs; `Warp_DrawBindless` draws three textures, one unbound, through the recorder; `Hlsl_Compute` and `Warp_RenderGraph` for the compute stages and the graph; `Hlsl_ColorSpace`, `Warp_HdrScene`, `Warp_HdrCopies`, `Warp_HdrEncode`, `Warp_CombineLut`, `Warp_Exposure`, `Warp_Bloom` and `Warp_LocalExposure` for the HDR scene; `Warp_GBuffer` and `Warp_MotionVectors` for the G-buffer; `Warp_LightTarget`, also as `Gpu_`, for the light target; `GpuScene_Ranges`, `GpuScene_ShadowLatch` and `Warp_GpuScene` for the GPU scene; `Warp_RtTlas`, `Warp_RtBlasCache` and `Warp_RtSkin`, each also as `Gpu_`, for the acceleration structures; `Warp_RtHit` and `Warp_RtReflection`, also as `Gpu_`, for the traced passes; `Noise_Table` and `Warp_RtDraw`, also as `Gpu_`, for the render programs that trace; `Warp_RtShadows` and `Warp_RtHistory`, also as `Gpu_`, for the traced shadows and their history; `Warp_RtIndirect`, also as `Gpu_`, for the indirect light; `Warp_RtGlossy`, also as `Gpu_`, for the glossy reflections). `build/vs2022-x64/bin/Release/d3d12Tests.exe <filter>` runs the tests whose names contain the filter, `all` every test.
- The visual gate is `tools\vdemo\compare-apis.ps1 -Stage <name> -Demos <list> [-Gbv] [-Hdr] [-Warmup <demo>] [-ExtraArgs <cvars>] [-Baseline <run>]`. Two D3D12 runs, with and without the debug layer (and with `-Gbv` a third under GPU-based validation), must give byte-identical frames and no layer message. `analyze.py` then holds the frames to the bars of `tools/vdemo/bars-d3d12.json` against the OpenGL reference (`-Baseline`, by default `research/vdemo/gl-ref`: the last local OpenGL run of the demos before the backend was removed, which cannot be made again, so keep it; `research/vdemo/d3d12-ref` keeps the D3D12 frames of the last gate). These runs get `+set r_hdr 0`, the frames OpenGL can be held to; `-Hdr` keeps the HDR scene and holds the frames to `research/vdemo/d3d12-hdr-ref`, those of the last HDR gate, with ray tracing on as by default (`-ExtraArgs '+set','r_rayTracing','0'` gives the frames without it; `analyze.py --luma` compares the mean brightness of two runs per demo). Run `_x4_gui` with `-ExtraArgs '+set','r_clear','2' -Baseline research\vdemo\gl-ref-clear` (GL's frames with the same cvar), and `_x7_heathaze` in a call of its own. A lone 2x2 or 4x2 brighter block in one frame of one run is a known AMD driver flake: run the pair again, it must not repeat. A `window: client` line in the log means another program moved or resized the window: the frames from there on do not compare (the size change also resets the eye adaptation), and the gate fails when such a line falls into a compared demo. When it happens at a fixed time after start, `-Warmup <demo>` runs that demo first in every run and leaves it out of the comparisons. A `profile save failed` warning in the log means the game's dialog lies over the frames from there on: run it again. Under the auto exposure such a block moves the measured EV100 by about 1e-5; rarely (about once in 15 demos) that crosses a step of the target, and the pair then differs by 1 LSB over the frames of a few seconds: the same rule applies. Under GBV the reception cinematic of `07_cinematic` once ended early (the PDA open from tic 1562, `No cinematic to skip.` in the log): sound time is the real clock, so a slow run can move script waits; it is not the renderer, run it again.
- Direct3D 12 has to look no worse than OpenGL, not the same: driver filtering differences, compiler last-bit noise and thin edge lines are fine. Judge a bar miss by eye on the heat maps and contact sheets that analyze.py writes.
- Names stay in their folder: Direct3D 12, DXGI and DXC names only in `neo/renderer/D3D12/` and `neo/tests/d3d12_*`, OpenGL names nowhere (renderApiLeaks). Shared code calls `renderBackend` only.

## Editor

- `editor/` holds the level and material editor, in one process and two modules. `Doom3Editor.exe` is the same engine objects as the game (`d3bfg_link_engine`) plus `editor/bridge/`, the engine-side half. `editor/ui/` is the Qt 6 interface, built as `bin/<Config>/editor/Doom3EditorUI.dll` with the Qt DLLs next to it; the exe loads it at start. Sources are listed in `editor/sources.cmake`.
- The two halves share only `editor/api/EditorEngineApi.h`: pure interfaces, plain data and `const char *`, no ownership across it. No Qt code may share a module with the engine (its `operator new`, the `Str.h` macros, the static CRT), so `editor/ui/` includes no `neo/` header and `editor/bridge/` no Qt header.
- Qt is not in the repo: `tools\qt\install-qt.ps1` downloads a kit into `external\qt-x64` (gitignored; `-DD3BFG_QT_ROOT=<kit>` points elsewhere), then re-run the configure. Without Qt the UI target is skipped and only `--bare` works. Copy the `editor` folder into the game install with the exe.
- The engine is embedded through `idEngineHost` (`neo/framework/EngineHost.h`). `engineHost` is `nullptr` in the game, so every branch on it is dead there. A host owns the top-level window and the message loop and drives `Sys_EngineInit`, `Sys_EngineFrame` and `Sys_EngineShutdown` (`sys/win32/win_entry.h`); the engine window is a child of the host's, with no intro, legal splash, main menu, gamma ramp or single-instance check. It is active (keys, mouse grab, sound) while it has the keyboard focus: a click gives it, Shift+Esc gives it back.
- Editing is not a running game. `editor/bridge/EditorWorld` holds the `idMapFile` as it is on disk (`Parse` with `asWritten`) and a render world of its own: the map's `.bproc` plus a render entity or light per map entity, made by `idGameEdit::ParseSpawnArgsToRenderEntity/RenderLight`. The host draws it through `idEngineHost::DrawScene()` while no game map runs. `EditorView` is the fly camera; in edit mode it takes the engine window's mouse and key messages, so the engine never becomes active.
- Editor console commands: `editorOpenMap <map>`, `editorCloseMap`, and `editorCheckMaps [filter]`, which reads, writes and reads again every retail map and compares the geometry CRC, entities and keys (`Doom3Editor.exe +editorCheckMaps +quit`; it must report 0 failed, or saved maps would lose their `.cm`/`.aas`).
- The map file is the document: an edit replaces an entity's key/values (`idEditorWorld::SetMapArgs`) and is one step of `idEditorHistory`. `editorSelect <entity>`, `editorSetKey <entity> <key> [value]`, `editorUndo`, `editorRedo` and `editorSaveMap` do from the console what the viewport and the menus do, so edits can be tested without a mouse.
- An entity keeps its index while the map is open: a removed one stays in the list without key/values (undo brings it back) and `idMapFile::Write` skips it. `editorCreate <entityDef>`, `editorDuplicate` and `editorDelete` work on the selection. The editor mounts every map's resource file (`idFileSystem::MountAllMapResources`), so media of any map can be used in any other.
- `editorSaveMap` writes `maps/<name>.map` into `fs_savepath`, never into the game install. The editor sets `fs_resourceLoadPriority 0` so the loose file wins over the resource files; the game needs the same cvar to load a saved map. Moving a brush entity changes only its `origin` key.
- Preview pictures (`idEditorEngine::RequestPreview`, `editor/bridge/EditorPreview`) are frames nobody sees: a world of one model and two lights is drawn into a corner of the output (`CropRenderSize`; a cropped `RenderScene` fills the crop and skips the post process), read back with `idRenderSystem::ReadLastFrame( ..., discard )` and never shown (`presentMode_t::NONE`), so the screen keeps the frame before. One picture a frame, every other frame while a map is open. `editorPreviewTest material|model|class <name> [size]` writes one to `editor_preview.tga` in `fs_savepath`.
- The Content Browser (`editor/ui/ContentBrowser`, `ThumbnailCache`) lists materials, models, entity classes, sounds and maps (`idEditorEngine::EnumAssets`; the retail models exist only as `generated/rendermodels/*.b*` in the resource files, `idFileSystem::ListResourceFiles`). Its pictures are previews, kept as PNG files in the user's cache folder; only what is seen is asked for.
- Images loaded for a preview carry `idImageManager`'s load mark and are purged every 64 pictures, so memory stays flat over the whole game data; a purged image loads again when something binds it. `editorPreviewSweep material|model|class [first] [count]` makes every picture and throws it away (the memory and crash test).
- An asset can stop its frame with an engine error (a material whose program does not exist): the preview is dropped (`OnPreviewReady` with width 0) and the next one waits 250 ms, because several errors within 100 ms become a fatal one. A material with a deform is shown on a quad: a tube deform on other geometry is a `common->Error` on a job thread, which ends the process.
- The material editor (`editor/ui/MaterialEditor`) edits one declaration as text and as a list of keys at once. `editor/mtr/MtrText.h` (header only, neither Qt nor the engine, used by both halves) parses the text into lines and blocks that only point into it, so an edit replaces the bytes of one value and comments, spacing and line ends survive. Apply is `idEditorEngine::ApplyMaterialText` (`SetText`, `Invalidate`, `EnsureNotPurged`: live, no file); Save is `idDecl::ReplaceSourceFileText`, which now writes the `.mtr` into `fs_savepath`.
- `editorCheckMaterials` parses every retail material and writes every value back (`Doom3Editor.exe +editorCheckMaterials +quit`; it must report 0 failed). `editorSetMaterialKey <material> <key> <value> [save]` and `editorEditMaterial <material>` do from the console what the panel does.
- Play in Editor (`editorPlay`, F5) saves the map when it has changes and runs `devmap` on it in the viewport; `editorStop`, Shift+Esc (`idEngineHost::OnEscapeToHost`) or the game's own exit ends it. While it plays, `idEditorWorld::Suspend` has freed the editor's render world and the preview's and kept the document, the history, the selection and the camera; `Resume` builds the world again. Both worlds at once do not work: a level load purges the models and images the other holds, and the map's geometry does not fit the static vertex cache twice (so the game's world is emptied after a stop). In a host `idCommonLocal::LeaveGame` makes no main menu.
- A loose `maps/<name>.proc` (one a map compiler wrote) decides what the render world loads: a `.bproc` with another timestamp is made again, also in production mode. `generated/*.bproc`, `.cm` and `.bcm` are written into `fs_savepath`. With `fs_resourceLoadPriority 0` `idFileSystem::GetTimestamp` answers with a loose file's own time (it was 0 for every name the resource files have). `renderWorldInfo` prints where the game's world was read from and what it holds.
- `editor/compilers/dmap/` is the map compiler of the original Doom 3 GPL release (the OBJECT library `MapCompilers`, linked into the game and the editor by `d3bfg_link_engine`, /W4 and /WX). `dmap <map>` writes `maps/<map>.proc` and `.cm` into `fs_savepath`, or a `.lin` when the map leaks; it refuses to run while a game map runs. `testmap <map>` compiles and loads. It works on float vertices of its own (`dmapVert_t`, `dmapPatch_t`): `idDrawVert` is packed. Not ported: the OpenGL debug views, the precomputed shadow volumes and light carving (the engine makes the shadows itself, 4-10 % of a frame, `research/perf.md`).
- A map without a resource file of its own gets every map's resource file mounted (`idFileSystemLocal::BeginLevelLoad`, and at the start of `dmap`): an image that is not found once stays the default one. The test maps are `base/maps/editor/box1.map`, `box2.map` (2 areas, 1 portal) and `leak.map`; two `dmap` runs must give the same bytes.
- `dmapCheck [part of a map name] [keep]` compiles every retail map (`dmap noCM`) and compares the world with the retail `.bproc`: areas, portals and models must be equal; nodes, vertices, triangles, zero-area and duplicated triangles are printed (`Doom3BFG.exe +set fs_resourceLoadPriority 0 +dmapCheck +quit`, 60 maps in about 11 minutes, it must report 0 failed). With a filter it also prints the models and surfaces that differ most; `keep` leaves the `.proc` in `fs_savepath`.
- The original compiler ran on the x87 FPU in extended precision. The 2D tests of `optimize.cpp` are evaluated in double (`CrossZ`, `Dot2D`): in float they pass collinear triangles, which the t-junction fixers then split many times over. A patch is compiled from the float texture coordinates of the map file (`idMapPatch::GetFileTexCoord`): the 16-bit ones of `idDrawVert` put a split vertex beside its edge, and the derived tangent turns.
- A host has no main menu (it would play the menu music), so nothing tells the engine to let the mouse go: `idCommonLocal::Frame` releases it while no map runs in a host. Grabbed, the DirectInput mouse is exclusive and no click reaches the editor's viewport.
- The compiler is called through `CompileMap( options, result )` (`editor/compilers/MapCompiler.h`): a progress callback, a cancel check asked inside the long loops, and a status `OK`, `LEAKED`, `CANCELLED` or `FAILED`. An error inside the compiler comes back as `FAILED`; afterwards the compiler holds no memory and no state. Its structures live in one arena (`DmapArena.h`), freed as a whole. A cancel is not asked once the `.proc` is being written, so a new `.proc` never stands beside an old `.cm`.
- A change of the compiler must not change its output: compile `editor/box2` and a few retail maps (`dmapCheck <map> keep`) before and after and compare the bytes. `dmapCheckAbort <map>` cancels and raises an error at several points of a compile and checks that the next clean compile gives the same file; every error it raises is copied to the clipboard by the engine.
- `editor/compilers/aas/` is the AAS compiler of the GPL release (the file reader and writer were already in `neo/aas/`). `runAAS <map>` writes `maps/<map>.<aasN>` into `fs_savepath` for every `aas_types` setting the map's entities use; `runReach <map>` redoes the reachabilities. It needs the map's text `.proc`, so run `dmap` first: retail maps have none, and without it a different file comes out. `CompileAAS( options, result )` is the entry, like `CompileMap`. A map without a monster gets no file.
- `aasCheck [part of a map name] [keep]` compiles the `.proc` and the AAS of every retail map and compares the counts with the retail files (81 files in about 8 minutes; `game/erebus6.aas96` is 2 reachabilities over the tolerance). `aasCheckAbort <map>` tests the cancel. `base/maps/editor/monster.map` is the test map: with its `.aas48` the zombie comes through the doorway. `aiStatus` (a game command) prints each monster's origin, AAS, enemy and distance to the player.
- `idBrushBSP::UpdateTreeAfterMerge_r` walks the whole tree: the original's bounded walk missed a reference to a freed node on `game/caverns1` and corrupted the heap.
- Brushes: `editor/bridge/EditorBrush` makes windings and render models from brush sides with dmap's texture math, so a face looks the same before and after compiling. A map shows its compiled world while its `.proc` is current (a loose `.proc`, and a `.cm` whose CRC is the map's). A primitive edit, or no current `.proc`, makes it "geometry dirty": the editor draws preview models until `editorBuild` succeeds; undo does not go back to the compiled world. Preview geometry is one render model per 512-unit cell per map entity, never one per primitive: a render world holds 10000 entity defs.
- `editorNewMap <name>` starts a map from nothing. `editorCreateBrush`, `editorSelectBrush <entity|world> <primitive> [face]`, `editorMoveBrush`, `editorMoveFace`, `editorHollow <thickness>`, `editorSetFaceMaterial`, `editorSetFaceTexture`, `editorMakeEntity <entityDef>`, `editorMoveToWorld` and `editorGrid <units>` edit brushes, one history step each. The selection is entities or brushes, never both; a face only when one brush is selected. A worldspawn patch is selected and edited as a whole like a brush (move, rotate, duplicate, delete, material); its control points are not edited and no new patch can be made.
- `editorRotateBrush <x|y|z> <degrees>` turns the selected brushes and patches around the selection's centre, texture-locked; quarter turns keep the planes exact. `editorListPatches` prints patches for `editorSelectBrush`. `base/maps/editor/patch1.map` is the patch test map.
- `editorBuild [fast]` saves, runs `CompileMap` and then `CompileAAS` when an entity's def has `use_aas` (`fast` skips it), and loads the fresh world. It blocks the frame and pumps the host's events for the progress and the cancel. A leak keeps the preview and draws the `.lin` in red (`editorShowLeak`); `editorPlay` on a geometry-dirty map builds first and does not start the game when that fails.
- A visportal is a brush across the whole opening with `textures/editor/visportal` on one face and `textures/common/nodraw` on the others (`editorCreateBrush ... textures/editor/visportal` makes that). `tools/editor/build-test-map.cfg` builds, compiles and plays a two-room map with a monster from nothing (`Doom3Editor.exe +exec` it from `<fs_savepath>/base`): it must print 1 area, then 2 areas and 1 portal, then 1 AAS file, and `aiStatus` must show the zombie closing in.
- The Qt side has a test hook: `Doom3Editor.exe --ui-script <file>` (`editor/ui/UiScript.h` lists the commands; objects are found by `objectName`, so give new actions and tested widgets one). `tools\editor\run-ui-smoke.ps1` runs `tools/editor/ui-smoke.txt` (new map, box, hollow, build, play, faces, 2D view, leak, cancel) and must end with 0 failed.
- Posted window messages, `editorClick`/`editorDrag` and the UI script's Qt events do not prove real input: an engine that held the mouse exclusively passed every scripted test. Check a new mouse feature once with the real mouse, with the editor in front.
- Brush tools: Select (Q), Box (B: drag on a face or on z = 0), the move gizmo for a brush and one arrow for a selected face, the rotate gizmo (E) with the Angle step, the 3D grid (G), Hollow (Ctrl+H), Build F7 and Shift+F7. The 2D view (`editor/ui/OrthoView`) is drawn by Qt from `EnumViewBrushes`/`EnumViewEntities`, at most 4000 brushes around the view. The editor API is version 11.
- Without a map the editor draws an empty viewport itself; left to the engine, it would show the game selection screen.
- `renderEntity_t`, `renderLight_t` and `renderView_t` are zeroed with `memset`, never `= {}`: `idVec3` and `idMat3` have empty constructors of their own, so `= {}` leaves them unset (a light with a garbage `lightCenter` lights nothing).
- The editor always runs with `com_smp 0`: nothing of a frame is pending between two frames, so the bridge may change the world, the decls and the render world there.
- `Doom3Editor.exe --bare +devmap <map>` is a plain Win32 frame around the viewport with the game's own input, for testing the hosting. It also runs the visual demos (`+vdemo <name> quit`): its frames are byte-identical to the game's.

## Code conventions that bite

- **Write modern C++, standard C++23.** New and changed code uses the current language: `nullptr`, `constexpr`, `auto`, range-for, lambdas, `enum class`, `std::unique_ptr`/move semantics, `override`, `[[nodiscard]]`, `std::span`/`std::string_view`, and so on. Don't add things deprecated or removed since C++17:
  - `register`;
  - `std::auto_ptr`;
  - arithmetic or comparisons between different enums, or between an enum and a float;
  - `==` on arrays;
  - literals into `char *`.
- The existing code is C++03-era id style. Modernize what you touch, and keep it compiling in all three configs.
- **Breaking changes are fine.** There is no public API: the engine, the game code and the tools build into executables from this repo, with no mods or outside callers to stay compatible with. Change interfaces (`idGame`, `idRenderWorld`, `idCommon`, ...) and update every caller. Rewrite or refactor bad code instead of working around it. Only the retail game data (maps, defs, scripts, GUIs) has to keep loading.
- **Comments: at most 3 lines, compact and to the point.** A comment says what the code can't: why, a constraint, a trap. Don't repeat the code or state the obvious. Exceptions: diagrams and architecture documentation.
- `idlib/Str.h` macro-redirects the CRT string compares. `strcmp` silently becomes `idStr::Cmp`, while `_stricmp`, `strcasecmp`, `strnicmp`, `_memicmp` and similar become undefined `use_idStr_*` tokens and fail to compile. Call `idStr::Cmp`, `idStr::Icmp` or `idStr::Icmpn` directly.
- Source files use CRLF line endings. Keep them CRLF when editing with scripts, because `sed -i` and heredoc appends introduce LF.
- `idlib/Heap.cpp` replaces every global `operator new`/`delete` form (sized, nothrow, `std::align_val_t`) once, out of line, plus the tagged `new ( TAG_X ) T`. All of them, `Mem_Alloc` and `Mem_ClearedAlloc` use `_aligned_malloc`, so that memory must never reach the CRT's `free()`, and `malloc` memory must never reach `delete` or `Mem_Free`. Don't define `operator new`/`delete` inline anywhere (C4595). `new` throws `std::bad_alloc` and never returns NULL.
- Settings live in cvars (`idCVar` globals with flags such as `CVAR_ARCHIVE` or `CVAR_SYSTEM`). Externs for game cvars go in `d3xp/gamesys/SysCvar.h`.

## Running and diagnosing

- Game data is not in the repo. You need a retail DOOM 3 BFG install, and the built exe is copied into it. `testing_1/` … `testing_5/` are gitignored local installs. `testing_1/Doom3BFG_perf.bat` launches with logging and the perf cvars below.
- The repo's `base/` holds `default.cfg`, `shaders/` (the HLSL of Direct3D 12), the visual demos `vdemos/` and our own test maps `maps/rt/` with their materials (`materials/rt_lab.mtr`) and textures (`textures/rt/`).
- `tools/rt/make_gallery.py`, `make_lightlab.py` and `make_lab_textures.py` write those maps, materials and textures, the same bytes on every run: change the script, never its output. `rt/gallery` (demo 20) is built of retail materials; `rt/lightlab` (demos 27-30: shadows, bounce, emissive, glossy) of materials whose albedo, specular and emission are known numbers, in closed rooms that share no wall. A diffuse map is read as YCoCg: a flat colour is `textures/rt/white.tga` times a stage colour, never `_white` (a little yellow there) or `_black` (blue).
- Visual demos are scripted scenes on the retail maps (`base/vdemos/*.vdemo`), stepped by a virtual 240 fps clock, so their frames repeat exactly from run to run. They are for regression checks:
  - `tools\vdemo\run-vdemos.ps1 -OutDir <dir> [-Demos 01_camera,...]` deploys the Release exe and the demos to `testing_1`, runs them and collects the frames;
  - `tools/vdemo/analyze.py <run> --baseline <run>` compares two runs (SSIM, repeats, pops);
  - in the game, `vdemo <name>|all [quit]` runs them, `vdemo_capture 0` skips saving the frames and `vdemo_realtime 1` plays them at real speed for watching (`testing_1/vdemo_<name>.bat` and `vdemo_all.bat` start them that way).
- A model that is not found is never written to `generated/`: with `fs_resourceLoadPriority 0` its loose stub would hide the real binary of a resource file from then on. A "Model ... defaulted" for a retail model means such stubs (about 1.4 KB each) lie in `base/generated` of the install: delete them. Generated models go to `fs_savepath`. A stub also changes the game: 03_physics spawns `moveable_cartonbox1`, whose `tbox1.ase` the retail data lacks, and a stub `tbox1.bcmodel` gives it another collision, so the scene drifts from tic 155. An exe of an older commit writes such stubs again.
- With `+set logFile 1`, the console log is written to `%USERPROFILE%\Saved Games\id Software\DOOM 3 BFG\base\qconsole.log`. The log survives a game crash.
- `logFile 2` also calls `FlushFileBuffers` after every print. That costs milliseconds per line, so it skews perf measurements. Use it only when Windows itself crashes or hangs.
- Useful diagnostics:
  - `com_showFPS 1`: the perf overlay. `com_showFPSScale` sets its size.
  - `com_speeds 1`.
  - `g_frametime 1` and `g_timeEntities <ms>`: per-entity think timing.
  - `r_showPrimitives 1`.
  - `r_pix 1`: GPU and CPU ms per render pass (the `renderLog.OpenMainBlock( MRB_* )` blocks), printed about once a second from GPU timestamps read back a few frames late, so nothing stalls. It also adds the top 3 GPU passes to `com_showFPS`. `r_pix 2` wraps the passes and render log blocks in debug groups (PIX events) for PIX, RenderDoc, Radeon GPU Profiler and Nsight, and `r_pix 3` does both.
  - `cm_traceStats 1|2`: per-second collision query cost by model, and with 2 also the slowest queries.
  - `sys_profile 1` together with `sys_profileTop`, and the commands `profileStart`, `profileStop` and `profileReport`: the game-thread stack sampling profiler. It resolves symbols via dbghelp, which needs the PDB next to the exe.
  - `testVideo <video/file.bik>` (cheat) plays a video over the 3D view; `exportVideo <video/file.bik>` writes its frames as TGA files to `fs_savepath`. The startup log says whether the FFmpeg DLLs were found ("Bink videos: FFmpeg ...").
